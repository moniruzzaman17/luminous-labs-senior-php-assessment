# AI work evidence

| Area | My direction | Initial AI output | Review finding | Final decision | Verification |
|---|---|---|---|---|---|
| Architecture and scope | Use one Laravel/MySQL assessment package with ticket-specific controllers, services, commands, models, and tests; keep infrastructure minimal. | AI generated the application structure and implementations for all three tickets. | The package remained reviewable without a frontend, queue, dashboard, or generic repository layer. | Keep the small conventional structure. This packaging is not a shared-production recommendation for unrelated clients. | Route inspection, full suite, and staged diff review. |
| Payment duplicate comparison | Make MySQL uniqueness, rather than a check-before-insert, the authority for one order per payment. | The first uncommitted draft compared incoming integer money with an uncast MySQL-hydrated value. | AI self-review found that a valid retry could be misclassified as conflicting. I did not identify this defect independently. | Cast `Order::amount_minor` to integer and compare only after the losing insert observes the durable row. | `PaymentWebhookTest` retry cases and `WebhookConcurrencyTest` against MySQL. |
| Provider retry behavior | Acknowledge only durable success and keep temporary failures retryable. | The first implementation treated verified permanent validation failures like retryable failures. | AI-assisted review found that this could cause useless repeated delivery. | Acknowledge permanent rejection as `rejected`; return `503` with `Retry-After` only for temporary processing/storage failure. | Malformed, validation, conflict, and failure/recovery tests in `PaymentWebhookTest`. |
| Safe failure context | Make processing failures inspectable without exposing secrets or internal details. | An earlier reporter included exception messages. | AI-assisted review found that messages could contain SQL or credentials. | Retain a controlled reason, verified identifiers where available, and exception class only. | `WebhookFailureInspectionTest` checks real files and command output for safe context and excluded markers. |
| Event identity | Treat event ID and payment ID as different identities. | Payment uniqueness existed, but provider event identity was not independently constrained. | AI-assisted review found that reusing one event ID for another payment was not durably prevented. | Add an independent `provider_event_id` unique index and classify identity reuse as a permanent conflict. | Reused-event and different-event/same-payment tests in `PaymentWebhookTest`. |
| Test database safety | Never let destructive test traits reach a development database. | The first guard ran after `parent::setUp()`. | AI self-review found that Laravel database traits could run before the database-name check. I did not identify this defect independently. | Guard in `Tests\TestCase::createApplication()` before test traits execute. | A deliberate development-database run was refused without changing seeded rows. |
| Historical shipment safety | Prevent future corruption without inventing repairs for existing data. | The representative importer initially used `updateOrCreate`. | AI self-review found that an import could overwrite historical evidence. I did not identify this defect independently. | Use append-only inserts in one transaction; keep historical audit read-only pending source evidence and approval. | Import rollback/conflict and non-mutating audit tests. |
| Webhook operational reporting | Separate untrusted security traffic from verified payment failures; keep processing as the normal operational view. | A later AI-assisted version mixed both categories in one reporting stream. | I identified that public invalid-signature traffic could hide genuine payment failures. | I required separate security and processing methods/destinations, sanitized security records, and no blanket endpoint rate limit. AI implemented that direction. | `WebhookFailureInspectionTest`, real invalid/signed requests, and `webhooks:failures` processing/security views. |
| Marlow access decision | Do not invent authentication while the intended audience is unknown; keep access closed until deliberately approved. | The endpoint was default-closed but also hard-blocked in production even when explicitly enabled. | Evaluator review found that approved configuration could never take effect in production. | Use one default-off flag consistently. Enabling it explicitly approves the limited public fields; restricted access still waits for intended-user details. | `UpcomingEventTest` covers default denial, explicit production enablement, fields, filters, limit, and order. |

The final submission is AI-assisted; I own the architecture constraints, risk priorities, review criteria, acceptance threshold, and final engineering decisions.
